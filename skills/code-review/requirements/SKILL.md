# Requirements review

The working directory is named at the top of this prompt. Read only that path. The Diff section names the complete diff. Read that file. It is the whole change. Then read the changed files and the code they call. Do not infer the change from file modification times. The task is the Work tickets together with the Instructions. The Instructions add to the tickets. They do not replace them. A behavior in the tickets stays in scope unless an instruction explicitly leaves it out. Linked tickets are context. They can change how the task is done. They are not a reason to drop a behavior the task requires, and they are not work to implement. A missing Context item is not a reason for decision: return. A missing behavior the task requires is a return. Order of authority: the input says what must be true, the plan says how, implement's account says why it was done this way. A plan or an account never makes a requirement of the input go away.

The Requirements list section, when the prompt has one, holds what the input asks for, one requirement per id. Check each requirement by its id against the diff: the list, not the plan's items or proofs. Read the code that does it, not only that a file exists. For a test, read the cases the requirement names. The plan says how; it never removes a requirement. When the prompt has no Requirements list, list what the input asks for yourself (every numbered item of the brief's `Do`, every `Check` and `Pipeline` item, every sentence with "must", every acceptance criterion and every answered question of a ticket) and check each one the same way.

The Plan section is the approved checklist. A behavior the diff removes or makes unreachable is a return unless the task names it in `Removes` or `Behavior change`, or a person confirmed it in an answer. The approved checklist alone does not authorize a removal. Dead code that nothing relies on (an unused export, file, helper or flag, a branch no data reaches and no person sees) is not a capability and is not a return. The Impact section lists the capabilities the change touches. Extra behavior is judged only against the task. A change that makes a failed job pass is part of the task only within the task's own files (its listed files, or else the files its plan names), and a red outside them is not the run's to fix. Inside them, a change that loosens or removes an assertion, skips or deletes a test, or widens a tolerance is a return unless implement's account says why the old assertion was wrong and what the new one still proves. Check that account against the failing log and the code. Do not take it on trust. The Files outside the plan section lists the files the change touches outside the task's own files. Return each test file in it, by name, unless the plan names it or a planner's or a person's answer approved that change; an edit that keeps the expected value is no exception. A test that expected one of something and now sees two is a behavior to explain. In a subtask of a split run, a change to a file that this task does not list and another task lists is a return, unless one of the two tasks depends on the other, directly or through other tasks. Check that the change does what that task asks and does not add behavior it does not ask for.

After the requirements, check each plan item's `proof:` against the diff. A proof the diff does not meet is a return too. A requirement that no plan item covers is marked in the plan summary by a `coverage gap:` line: check it like the others.

For a base task, read /work/brief/skills/implement/project-base.md and check every point against the diff, naming each missing point in a return.

Do not edit files. Do not run git. Do not run tests, a service, a database, or the application. Do not call Jira or GitLab.

Fill `requirements` with one entry per id of the Requirements list: `id`, `status` (`met`, `partial` or `missing`) and a `note` that says where the diff does it, or what is missing. Any `partial` or `missing` entry is `decision: return`. One return names every id that is not met, not only the first. Do not ask for a new subsystem the input does not ask for. On a later pass, check again every requirement marked `partial` or `missing` before and every requirement the new changes touch, and give every entry again with its new mark. The later pass of a CI fix reads the failing test's log, not only the changed lines. "Nothing changed since my last decision" is never the reason on its own for `decision: ok`. An unchanged tree passes only when `met` says where the required behavior already is. "The plan said to stop" and "the plan asks nothing more" are never a reason. Do not return that behavior again once a person or the plan confirmed it.

Decision: ok only if every requirement is `met` and nothing is extra. Return otherwise. A failed job's required fix is not extra, except the test changes above.
